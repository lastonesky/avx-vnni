---------------------------------------------------------------
    c (初始)             [0, 0, 0, 0, 0, 0, 0, 0]
    c += a*b (期望 24)   [24, 24, 24, 24, 24, 24, 24, 24]
    a=2, b=-3 (期望-24)  [-24, -24, -24, -24, -24, -24, -24, -24]
    vpdpbusd a=0xFE,b=1    [1016, 1016, 1016, 1016, 1016, 1016, 1016, 1016]
    -> 期望 1016 (= 254*1*4)，证明 a 被当成【无符号 u8】解释
    vpdpbssd a=0xFE,b=1    [-8, -8, -8, -8, -8, -8, -8, -8]
    -> 期望 -8 (= -2*1*4)，a 按【有符号 s8】解释
    base = INT32_MAX-100   [2147483547, 2147483547, 2147483547, 2147483547, 2147483547, 2147483547, 2147483547, 2147483547]
    vpdpbusd  回绕 ->    [-2147354209, -2147354209, -2147354209, -2147354209, -2147354209, -2147354209, -2147354209, -2147354209]
    vpdpbusds 饱和 ->    [2147483647, 2147483647, 2147483647, 2147483647, 2147483647, 2147483647, 2147483647, 2147483647]
    (回绕结果应为负数: -2147354209；饱和结果应为 INT32_MAX: 2147483647)

    scalar      = -24576
    avx2-sim    = -24576   OK

    [为什么需要 VNNI] 大幅值下 avx2-sim 会算错:
    avx2-sim (vpmaddubsw)  [65534, 65534, 65534, 65534, 65534, 65534, 65534, 65534]
    vpdpbusd               [129540, 129540, 129540, 129540, 129540, 129540, 129540, 129540]
    真值 = 255*127*4 = 129540
    avx2-sim 把 64770 饱和成 i16 上限 32767，最终得到 65534（错）
    vpdpbusd 直接累加到 i32，无中间饱和，得到 129540（对）

===============================================================
  要点小结:
   1. vpdpbusd = 一条指令做 u8*s8->i32 的 4 元乘加累加，取代
      vpmaddubsw + vpmaddwd + vpaddd 三条指令；且没有 16-bit
      中间饱和问题（上面 avx2-sim 算出 65534 就是活例子）。
   2. 4 路累加器展开用于掩盖 5-cycle 延迟；本例实测已到 ~350 GB/s，
      瓶颈是【2 个 32B load/cycle】的取指带宽，不是算力。
   3. 数据布局要顺着指令: 每个 lane 吃 4 个【连续】的 K。

   两个真实踩过的坑（本 demo 里都修掉了）:
   A. MSVC 的 _mm256_dpbusd_epi32 编成 EVEX(62 ...) -> 需要 AVX512-VNNI，
      在 Alder Lake/Arrow Lake/Zen4 上直接 #UD。必须用
      _mm256_dpbusd_avx_epi32 强制 VEX(C4 ...)；ml64 同理，只能手工 emit。
   B. Windows x64 ABI 下 YMM6-YMM15 是【非易失】的。手写汇编用了
      ymm6/ymm7 却不保存，会静默破坏调用方状态（本 demo 曾因此
      测出 3.7e-289 秒这种垃圾计时，100% 稳定复现，极难查）。
